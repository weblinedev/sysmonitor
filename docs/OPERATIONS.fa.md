# راهنمای بهره‌برداری SysMonitor

## از کجا وضعیت را ببینم؟

در تلگرام، گفت‌وگوی خصوصی بات را باز کن و `/start` بفرست. دکمه‌های وضعیت سرویس‌ها، منابع ایران، آپتایم، رخدادها و تست اعلان باید ظاهر شوند. فقط شناسه عددی مالک مجاز است؛ عضویت در گروه یا دانستن نام بات کافی نیست.

در وب، کنسول اصلی Uptime Kuma برای مدیریت مانیتورها و تاریخچه است. صفحه وضعیت `status/sysmonitor` خلاصه سرویس‌ها را نشان می‌دهد. در نصب خصوصی، ابتدا تونل Termius را متصل کن؛ اتصال تونل روی مک برای اجرای خود مانیتور لازم نیست، فقط برای دیدن وب لازم است.

## معنای پیام‌ها

| پیام | برداشت درست |
| --- | --- |
| 🔴 قطع | دسترسی از سرور پایش پس از تلاش‌های تنظیم‌شده برقرار نشده؛ علت هنوز مشخص نیست |
| 🟢 بازیابی | همان آزمون دوباره موفق شده است؛ سلامت تمام نرم‌افزارها را تضمین نمی‌کند |
| 🟡 در حال بررسی | آزمون هنوز در مرحله تأیید خطاست |
| 🔧 تعمیرات | مانیتور در وضعیت تعمیرات قرار دارد |
| ⚪ داده منابع قدیمی | نمونه تازه نرسیده؛ عدد قدیمی را وضعیت فعلی فرض نکن |
| 🟠 ارتباط با Kuma قطع | خود لایه پایش مشکل دارد؛ درباره وضعیت ایران نتیجه قطعی نداریم |
| 🧪 تست | آزمون مسیر دریافت یا ارسال پیام است؛ قطعی واقعی ایجاد نشده |

بات عمداً URL کامل، IP عمومی، خطای خام، مشخصات مشتریان و خروجی کامل sysreport را به تلگرام نمی‌فرستد. نام مانیتورها را هم فاقد اطلاعات محرمانه انتخاب کن.

## وقتی هشدار آمد

۱. وضعیت چند مانیتور را مقایسه کن. اگر سایت و WHM و cPanel هم‌زمان قطع‌اند، مشکل گسترده‌تر از یک صفحه است، اما هنوز می‌تواند مربوط به مسیر ترکیه به ایران باشد.

۲. تازگی گزارش منابع را ببین. قطع نمونه منابع همراه با قطع HTTPS نشانه کمکی است؛ به‌تنهایی خاموشی سرور را اثبات نمی‌کند.

۳. با نشست مدیریتی مجاز، وضعیت سرویس، منابع و خطاهای مرتبط را بخوان. قبل از تشخیص علت، سرویس‌ها را کورکورانه ری‌استارت نکن. بات اصلاً فرمان ری‌استارت ندارد.

۴. پس از رفع مشکل، هم بازیابی در مانیتور و هم عملکرد واقعی سرویس را بررسی کن. برای فروشگاه، پاسخ HTTP موفق جای آزمون خرید، ورود یا دیتابیس را نمی‌گیرد.

## آستانه منابع

CPU و RAM از ۹۰٪ و دیسک ریشه از ۸۵٪، پس از سه گزارش پیاپی هشدار می‌دهند. بازگشت به بیش از پنج واحد درصد پایین‌تر از آستانه، پیام بازیابی می‌سازد. نمونه‌ها حدود هر دقیقه ارسال می‌شوند. فاصله طولانی بین نمونه‌ها شمارش هشدار جدید را از نو شروع می‌کند.

در این نسخه، وضعیت سرویس‌های systemd در گزارش منابع دیده می‌شود ولی هشدار مستقل برای هر سرویس ساخته نشده است. هشدار دسترسی HTTP/HTTPS را Kuma مدیریت می‌کند. داده منابع هم تاریخچه نموداری مستقل ندارد؛ برای چنین نیازی Beszel گزینه توسعه بعدی است.

## نگهداری و تغییرات

- پیش از کار برنامه‌ریزی‌شده، پنجره تعمیرات Kuma را تنظیم کن.
- توکن بات، کلید API و توکن telemetry را در فایل خصوصی نگه دار؛ داخل چت عمومی، issue یا ریپو نگذار.
- هنگام تعویض توکن، فقط سرویس مربوط را با تنظیم جدید راه‌اندازی کن و دوباره `/test` و هشدار آزمایشی را بررسی کن.
- پس از به‌روزرسانی، سلامت x-ui، پورت‌های قبلی، حافظه مصرفی و نمونه‌های مانیتور را دوباره بررسی کن.
- بکاپ روی همان سرور کافی نیست؛ نسخه خارج از سرور و تمرین بازیابی لازم است.

## محدودیت مهم

اگر خود سرور ترکیه یا ارتباطش با تلگرام قطع شود، همین بات نمی‌تواند همان لحظه خبر بدهد. برای پوشش این حالت باید یک ناظر مستقل خارج از هر دو سرور وجود داشته باشد. تا وقتی آن مسیر نصب و آزمایش نشده، پوشش کامل قطع سامانه پایش نداریم.
